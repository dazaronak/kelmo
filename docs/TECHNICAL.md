# Technical context

Implementation reference for contributors: the flows, invariants and refusal codes behind each module. Read the [README](../README.md) first for the overview and [USAGE.md](USAGE.md) for using Kelmo; the other files in this directory describe one command group each.

## Runtime in one screen

Python 3.12/3.13; macOS and Linux. Default single-user local writer. One `kelmod` daemon (Rust) per machine serves
MCP over Streamable HTTP on 127.0.0.1 with a bearer token, hooks and the CLI, and supervises the cores it routes
calls to over the `kelmo/2` framing ([PROTOCOLS.md](PROTOCOLS.md)). SQLite journal, SQLite/FTS5/sqlite-vec archive, local pinned MiniLM embeddings (or an explicitly configured `[embedding]` chunk index, below), Git-backed Markdown/registry. Native Claude/Codex subprocesses are optional executors. No cloud account is required for local storage/search; configured model executors have their own authentication/network requirements.

```text
Claude Code / Codex --HTTP MCP--> kelmod --kelmo/2--> state core -> Service (journal, jobs, archive proxy)
kelmod hook, kelmo CLI --d.sock-->   |                 archive core -> archive/archive.db
ssh -> serve-client -> kelmod attach |                 embed core (Rust: token counts, embeddings)
                                     `-- on a shared client: edge core -> SharedClient -> uplink -> authority

packaging/kelmo -> entry.py -> cli.py -> Service
                                  |        |-- Journal (.state/journal.sqlite3)
                                  |        |-- ArchiveAPI -> LocalArchiveAdapter -> archive (archive/archive.db)
                                  |        `-- wiki.engine -> registry + wiki Git commits
                                  |-- mcp.server -> same Service, memory and graph tools
                                  |-- hook start -> Config + hot.render (no model required)
                                  `-- session hooks -> immutable snapshots + session jobs
state core jobs (or worker daemon) -> operations -> resolution executor -> session_worker.tick
session_worker -> extract chunks -> save note -> Service archive receipt
               -> reconcile candidates -> checked optional wiki application
graph queries/reads -> selected wiki snapshot -> refresh derived graph if changed
graph stats/doctor -> inspect source/index freshness without rebuilding
```

The shell launcher uses Python `-I -S`; the default `entry.py` restores only intended runtime imports. It is not a filesystem/network sandbox. `bootstrap.py`, `runtime.py`, `linux_runtime.py` and `packaging/kelmo-isolated` retain the separate isolation experiment; do not confuse those paths with the default launcher. The local test harness uses an OS fence externally.

An explicit wiki path cannot overlap the data root, and a new vault refuses a directory that already holds files (`E_WIKI_ENROLL`). Relative wiki roots relocate with their relationship; absolute roots stay absolute. Ownership markers prevent two independent data roots writing one knowledge repository. Recovery validates repositories before mutations and refuses conflicting edits/history. Preserve existing Markdown structure and unmanaged text.

`wiki/pages.py` validates the page grammar and derives a page's work status from its facts, so nothing is
stored that can disagree with them. `load_registry` accepts only the current format; an older registry is
refused with `E_CAPABILITY` and is never rewritten. A role belongs to the page model, not to a note, and
`pages.fact_revision` is the single place a fact revision for the file contract is computed: giving a fact a
role changes its revision, and a note captured against the old one conflicts rather than dropping the role.

Discovery and the editor's bounded view sit on top of that model. `pages.page_index`
answers one row per page, sorted by target, work rows carrying summary, priority and parent and every row
carrying the status derived at read time; `pages.page_facts` answers one page completely, entry and
revisions included. `wiki/context.py` composes them for one call: the index of one project, then the
complete facts of the pages the caller selected in the caller's order, then a one-line digest of the open
work on the pages it did not select, and `omitted` names every page and fact the budget could not hold —
an omitted fact is never read as a fact the store does not hold, because `page` returns it. The token
estimate is `wiki/policy.py`'s `TOKEN_ESTIMATE` (UTF-8 bytes / 2.5), the same measure the wiki budget and
`kelmo doctor` use, so a context budget and a vault budget are one measure. A store without a committed
registry refuses these reads with `E_GENERATION`; a page-model refusal reaches the CLI as `E_INPUT` carrying
the repair the wiki half named.

## Main write flows

### Manual capture and promotion

`Service.capture(content, filename, role, intent, idempotency_key)` validates content (one MiB ceiling), simple Markdown basename and declared role. A stable request key identifies exact source/name/role/intent; reuse with different input fails. Unknown/collector roles remain `captured`; implementer/reviewer/lead archive work can be queued. Promotion requires declared lead plus valid `wiki-changes` and real fact-check receipts. Legacy roles remain caller declarations. Adoption origins are separately issued by trusted controller bindings; a serialized origin or a lead role cannot grant REQUESTER evidence authority.

`Service.run(id)` claims work, loads and checks immutable evidence, then calls the archive adapter. Ordinary intake stores text, FTS, exact evidence identity and owning receipt atomically, even if vectors are pending. Retry can recover the archive receipt before the journal has recorded its archived stage. On a current registry a promotion runs as one editor request keyed by the attempt; a queue retry resumes that request while it is open, prepared or finished (the recorded answer is settled, the prepared intent published, or the receipt replayed) and opens a new request only after a refusal, so a retry never proposes the same facts twice. Legacy supersession requires indexed replacement admission before hiding its source. Checked registry changes still use the existing publisher; conflicts create durable Resolution jobs and `E_BUDGET` retains the archive receipt. Journal claims and the persisted writer identity fence completion. See [ADOPTION-CONTRACT.md](ADOPTION-CONTRACT.md) for the boundary and unresolved runtime acceptance.

Typed source intake uses `Service.capture_source` and `source_packet`. The existing
journal stores source metadata and its full-packet hash alongside the operation;
the original bytes stay in the source spool. This preserves producer identity and
observation time across restart without replacing the source with a generated note.
A plain `capture` derives its packet before the spool write, so an invalid filename
date is refused with `E_INPUT` and leaves no orphan source. A journal operation from
before typed metadata whose filename cannot describe a valid packet keeps its source
and fails with `E_CAPABILITY`; no replacement packet is fabricated. A capture runs only
on an idle journal connection, the archive stage and its outcome commit together, and
a missing exact evidence reference fails with `E_RECEIPT` instead of being invented.
A supersession hide uses the origin of the operation that requested it. A target that
already has a linked correction is refused, even when that correction's hide has not
landed yet; the archive rechecks this under its write lock and refuses reverse links
and longer cycles, while a retry of the exact linked correction completes its hide.
A resolution that cannot be created after a wiki conflict fails the operation in phase
`resolution_create`, keeping the first failure in its outcome. Dates at the contract and
Service boundary are ASCII `YYYY-MM-DD` calendar days.

The archive adapter stores exact per-version source/origin metadata. Same-ID update
snapshots the complete old row under the version lock and retains owning receipts.
History lists replaced versions only; ID-only public reads use the visible head.
A row an older archive accepted (an impossible calendar day, a trailing newline, empty
metadata) is never normalized: a typed read of that exact version fails with
`E_CAPABILITY` naming record and version, while `memory_get` still returns the raw row.
`memory_list` orders and filters by UTC microseconds; a row whose timestamp it cannot
read raises `ArchiveLegacyRecordError` naming every such record (`E_CAPABILITY` through
the adapter) rather than skipping or misplacing it.
With `[embedding]` configured, capture and same-ID update also cut the text into
fitted chunks and write them, their FTS rows and their vectors in the same write
transaction as the record (see the read flows below).

Resolution requests carry original evidence, source hash, archive reference and permitted current fact keys/revisions. Invalid proposals require another executor attempt; validated responses are durable and reused during commit recovery. Expired failure/refund callbacks cannot mutate jobs. A fact Resolution commit can encounter `E_BUDGET`; bounded retries retain its accepted response and can end in review. Reopen preserves original evidence. Durable-effect replay safety is not exactly-once model invocation or semantic correctness.

### Explicit actions and the registry projection

`ActionState.apply` / `GitIngress.ingest` -> `Service.action_coordinator` (`publication.py`) under `.state/worker.lock`: recover prepared intents -> replay by origin-scoped idempotency key -> verify the existing owning archive receipt -> reducer -> immutable journal intent -> `engine.publish_action`. The publisher re-reads that prepared intent; any other registry write that changes actions is refused (`E_OWNERSHIP`). Actions need a committed registry, which `kelmo init` creates; nothing migrates a registry when a store opens.

Git intake has two paths.

**Foreground capture (`GitIngress.capture`).** The trusted producer path calls it when the tool reports success, under an issued producer origin. It reads the repository at that moment:

- for a push, the remote-tracking ref Git just wrote and its previous reflog value, or the merge-base with the default branch for a first push;
- for a local merge into main/master, `HEAD`, `HEAD@{1}`, the merge reflog subject and the merged tip (the new head, or the second parent of a merge commit).

The command's real Git top-level must equal its enrolled root. Git resolves the top-level from the unnormalized directory the command named, so a nested repository, a symlink or `..` cannot borrow an enrolled worktree's refs (`E_BINDING`). A push capture also needs the receipt itself to name the enrolled destination (`To <url>`) and exactly one ref-update or new-ref line for the target; quiet or ambiguous output is refused with `E_EVIDENCE`, as on the raw path. An update line must agree with the tracking ref's previous value and its new value. A new-ref line attests a first push only with positive creation evidence: the tracking ref's file-backed reflog holds exactly one entry, a creation (null old value) at the current value. A missing reflog (`core.logAllRefUpdates=false`, expiry, another ref backend) is not evidence and refuses (`E_EVIDENCE`), as does any later entry: once the ref has moved, the old receipt cannot attest the current value. Two limits remain. The read happens in the foreground window after the tool reports success, so a second push landing inside that window is indistinguishable. Deleting a ref deletes its reflog, and the check does not tie the creation entry to the receipt. A branch deleted and then recreated before an old `[new branch]` receipt is captured, at the same value or a different one, therefore looks like that receipt's creation. The capture then attests the recreated value under the old receipt: the state is true, but the evidence binding is not. No clock window, hook or signature closes this; it is an open decision.

Where the tool output reports a destination or revisions, they must agree with that read. Capture then archives one packet holding the original tool receipt plus that immutable event or its refusal, and stores the observation on the request row. It reduces and publishes nothing.

Later `ingest` with the same packet and key consumes the stored observation and never reads refs again. It only confirms that the captured commits exist in the enrolled repository. A local merge matches the merge action by its merged tip and stays distinct from push and deployment. A packet carrying the capture mark with no capture under its key (a submitted snapshot) is refused with `E_EVIDENCE` before any intake or request row is written, so the refusal cannot pre-empt a lawful capture that later uses the same key.

Captures are archived under the reserved key namespace `state-capture/`; raw intakes use `state-intake/`. Public `Service.capture` and `Service.capture_source` refuse both prefixes (`E_INPUT`). Only the coordinator's private `Service._state_intake` writes them. `captured_git` trusts an operation only when all of these hold:

- it was found through the shared `Service.capture_request_key` derivation;
- it carries the same issued origin;
- it has typed `git_event` source metadata.

**Strict raw path (`ingest` without a capture).** A raw receipt with no capture row is bound to what the archived producer output itself attests, never to refs read at intake. A push needs:

- a `To <url>` line naming the enrolled remote;
- exactly one ref-update line, `<old>..<new> <src> -> <dst>` (or `...` for a forced update), whose destination is the resolved target.

The abbreviated names in that line resolve to unique commits in the immutable object store. A fast-forward merge needs one `Updating <old>..<new>` line plus `Fast-forward`, and the checkout must still contain the new revision. The following stay unresolved, recorded as a refused `E_EVIDENCE` intake with the receipt archived:

- the first push of a new branch (`* [new branch]`), which names no revision;
- merge-commit output;
- quiet output;
- a missing destination;
- an ambiguous abbreviation.

Up-to-date output is ignored. An R1 receipt replayed after the branch reached R2 therefore attests only R1. Through capture, the first push of a new branch and a merge commit both complete normally. A producer may never reuse the same output as a new transition of the same action (`E_STALE`). Sameness is computed over what the producer parser actually reads (`git_ingress.attested_receipt`, hashed by `state.tool_receipt_digest`): the command, the cwd, the normalized exit status, the no-op markers and the non-blank output lines without trailing whitespace. It is compared with the receipt behind every accepted PRODUCER event of that action. A byte-identical, re-serialized, capture-enveloped or hook-re-enveloped copy (other session or tool-use identifiers), or one differing only in ignored blank lines, therefore cannot reopen a retracted action. Each packet's full original bytes and its owning receipt stay archived as they were. A genuine rollback and re-push that prints the same projection is the same receipt here; whether such output should count as fresh completion is an open decision. An accepted event whose spooled source bytes cannot be read is `E_IO` and stays retryable.

Frame and reducer refusals before an intent is prepared settle the request row only for the deterministic codes `E_STALE`, `E_STATE`, `E_CORRECTION`, `E_CONFLICT`, `E_RECEIPT`, `E_BINDING`, `E_ORIGIN`, `E_INPUT`, `E_EVIDENCE` and `E_OWNERSHIP`. A retry under the same key replays the recorded code and is not re-reduced against a later head. Admission reduces against the committed registry of the pinned generation it reads first (`KnowledgeReader.registry(generation)`), never the working file. Before any reduction or settlement, `engine.require_clean_baseline` refuses with `DirtyKnowledge` (`E_CONFLICT`, typed, not recorded) while the working registry, manifest or a registered page has local edits. A generation, configuration, capability, storage (`E_IO`, `E_GIT`) or dirty-baseline failure therefore leaves the row open, and the same key, including a captured packet's, is admitted once the store is repaired. `E_CONFLICT` stays deterministic for conflicts the reducer itself finds.

The request settlement, its accepted history and the source outcome of a Git intake are written in one journal transaction (`Journal.action_begin`, `action_finish` and `action_refuse` with `outcome=`). This covers refused, ignored, unresolved, unchanged and published requests. A process death between those writes leaves neither, and recovery writes both together.

A Git intake whose archival operation ended terminally `failed` raises its error code with the operation ID and the repair: fix the cause, run `kelmo queue retry <operation>`, then resubmit the same request. `Service.run` returns a terminal operation unchanged, so resubmitting alone does not retry it. Retry is never automatic. `kelmo queue retry` renews the note's editor attempts and its worker retry budget; a retry the daemon or the session worker makes renews neither. A capture whose spooled source bytes cannot be read is `E_IO` in `captured_git` too, as at the other source reads.

A finished request replays before recovery, even while another prepared publication cannot finish. A pending apply keeps the owning operation it recorded and re-verifies that exact receipt; it never switches to a newer duplicate owner.

Failures after preparation are never settled there:

- a dirty path or an unrenderable page is a typed refusal (`E_CONFLICT`) that keeps its intent pending;
- a moved baseline settles as `E_STALE`, as before. `_complete` compares the intent with the committed registry of the current generation, so a working-file edit can neither fake a moved baseline nor hide a committed publication.

A non-UTF-8 path in the knowledge tree is `E_GENERATION`. `ContextBundle` refuses `complete` when `omissions` is not empty.

`pages.mandatory_paths` is the single mandatory selection:

- person pages: `person.md`, category `you` or layout `person`;
- every page holding a canonical mandatory record, meaning a fact marked `mandatory` or `protected`.

HOT (through `KnowledgeReader.mandatory(generation)`) and `KnowledgeReader.context` both select with it directly. `pages('person', …)` keeps its listing meaning, `person.md` only, so a protected project page is delivered as mandatory without joining the person listing. Each mandatory page is delivered whole, once: in `mandatory_rules` for context, where it is not repeated in `pages`, and first in HOT, whose header names the set as "mandatory pages". Overflowing mandatory content is `E_BUDGET` in context and in HOT. A registered page, or a fact target, absent from the pinned tree makes the whole generation `E_GENERATION` when it is loaded, so a mandatory page is never silently skipped; an unregistered `person.md` that does not exist is simply not part of the set.

An accepted action must be shown by at least one registered page (`pages.action_targets`). A topic or feature subject with no page, or a person or task action with no person page, is refused at admission with `E_BINDING`, a deterministic code that replays under the same key. No page is invented for it, and it is not moved to the person page.

A historical pin walks only commits reachable from HEAD that touch the manifest. A commit that deleted the manifest pins nothing and is skipped. A present manifest whose hash matches the pin but whose tree or registry does not validate is still `E_GENERATION`. A pin no reachable manifest measures is `E_GENERATION`; it is never answered from HEAD.

Whether a registry is committed is read at HEAD (`pages.committed_paths`), independently of whether the wiki can be read as a generation. A committed registry whose generation later fails still refuses; it never falls back to working pages.

A fact's target must be a registered page that is not a prose page. A fact's `role` and `index_target` keep their presence, an explicit null `role` included.

A publication that would rewrite a path with uncommitted edits refuses with `DirtyKnowledge` (`E_CONFLICT`, still a `RuntimeError`), naming every such path before anything is written. The working edit is not touched. For a new request this is detected before reduction and nothing is recorded. For an intent already prepared, recovery runs the same check (`require_clean_baseline`) before the publisher, whose working-file shortcut and reduction would otherwise report `E_PUBLICATION` or `E_OWNERSHIP`. The intent stays pending and later intake fails closed with the same typed reason and paths. A publication the committed generation already holds is recognized first and settles even while later local edits exist. Once the path is clean, the next request first publishes the pending intent. The generation digest covers the whole wiki subtree (except `entities.yml`, `_template.md` and `log.md`), not only managed regions or pages. Committing any hand edit or new page there outside the publisher therefore invalidates the digest, and the reader refuses that tree; a repair path is an open decision.

A publication renders every registered page from the single registry (`pages.render_v3_page`): contract frontmatter projected from the page entry (the publication sequence lives in the same commit's generation manifest, not in the pages), the layout headings in one `kb` region, action tables or general-action sentences, and a `narrative` region whose stale entries are labelled and quoted. Unmanaged bytes stay.

Every layout shows exactly its registered `links`. Adoption records in `links` the navigation earlier projections showed:

- an index page's detail pages, and a project hub's pages holding current facts;
- a feature page's parent and the pages linking to it;
- a project map's child pages.

Because a page shows the actions of pages it links to (`pages.action_targets`), a hub that now links a feature page also shows that feature's actions, and the feature's enrolled map pages must include it. A retired exact record leaves an ordinary page, but never a person page and never a mandatory or protected record. An unresolved record carries the frozen contract label `[unresolved legacy state; retained status: X]`.

Before an action intent is prepared, `_admit` renders the projected registry and runs the configured budget (`engine.check_budget`). A refusal is `E_BUDGET` with its repair text. It is not recorded as a settled refusal, and nothing is prepared, so the same key can be retried after repair. This prevents only failures predictable at admission. The environment can change after preparation: a hand edit grows a hub, or an instruction chain or the budget configuration changes. The publisher can then still refuse a prepared intent, and recovery fails closed for every later request until the condition is repaired. A page the renderer itself refuses keeps its existing publication-time refusal. Git and read failures in the check are typed `E_GIT` and `E_IO` and stay retryable.

On a page with a narrative region but no `kb` region, the new `kb` is inserted immediately before the narrative, so the next render accepts the order. Narrative-region text that no registered narrative owns refuses the render. It is never emptied.

A legacy header is replaced only when its exact bytes are recorded in the page's `compatibility.header`; ambiguous markers or a header changed since then refuse. Every publication renders every registered page's frontmatter from the registry, and unmanaged bytes come from the working file, which is why a local edit in any registered page refuses the publication (`DirtyKnowledge`). `doctor` and `wiki_committed` compare against the same projection at the committed sequence. Action repositories are checked against the `OriginBindings` at publication. StateAPI action publication, page registration and scoped editor publication use the single publisher.

`tests/test_state_publication.py::test_real_push_survives_process_death_without_second_publication` kills a real child process at two boundaries: before `publish_action`, and at `Journal.action_finish` after the commit. A fresh Service then recovers the same captured push exactly once.

Every registry write passes `engine.ownership_guard` inside `_preserve_v3`, whoever calls the publisher (StateAPI, editor, resolution or Dreaming): actions and their panels change only through the prepared StateAPI intent; protected rules, existing facts and narratives on a person page, person page entries and the `protected`/`mandatory` markers change only under an attributable rule-change intent; a new ordinary fact on a person page is allowed (it becomes `mandatory`, not protected); every person fact stays `mandatory`; no write removes a fact or narrative. A fresh revision does not help. A registry write that comes with no prepared intent and passes the guard still refuses with `E_CAPABILITY`.

### Scoped editor

`Service.editor.edit(source_operation_id, origin=, idempotency_key=, project=, selected=, executor=, budget_tokens=, rule_change=False, contexts=None)` edits a store from one archived source. Only an archived/applied operation with an exact owning receipt qualifies (`E_PERMISSION` otherwise); the archive receipt is never a publication receipt. Flow: replay by origin-scoped key → verify the source receipt → under the worker lock, finish prepared intents and check dismissal and quota deferral → record the `action_requests` row (`kind='semantic'`) with a consulting lease (900 s) → outside the lock, `wiki/views.editor_view` reads one pinned generation: the source, every mandatory page whole (`KnowledgeReader.mandatory`, the canonical `pages.mandatory_paths` set that generation context also uses: person pages and every page holding a protected or mandatory fact, from any project; delivery grants no edit scope, and rule changes still need explicit requester authority; a mandatory page that a selected page depends on carries its entities and revisions and counts for `depends_on` visibility, read-only unless itself selected; `E_BUDGET`, nothing sent, if they, the source or the reconciliation receipts do not fit), the project index (title and summary of every page of the project), then the selected pages and every exact expansion, in that order. A sent page is its registry entities and revisions plus its unmanaged text (`pages.unmanaged_text`: the bytes outside the frontmatter, a publisher-generated H1 and the kb and narrative regions, which render those entities), so each fact reaches the model once. Dependencies of a selected page (parent, links both ways, narrative and action subjects) are not pushed into the view: they stay index rows until the model asks for them, so a project map that every page links to costs one page instead of its project, and nothing the model did not ask for competes with a requested page for the budget. What does not fit is named in `omissions`; edit scope is every non-mandatory page sent (selected pages and expansions), and a narrative may depend only on facts and actions of sent pages, person pages and readable mandatory pages; `ContextBundle.complete` is false for partial, empty or stale context. The `ModelExecutor` receives a `ModelJob` and returns a `ModelOutcome`: `proposal`; `expand` with exact unsent index pages (at most two rounds); `reconcile`, which runs the existing `fact_checks.search` over the pinned facts and returns its receipts in the next payload as `reconciliations`; typed `failure`; or `deferred`, which only an adapter produces from a provider-level `QuotaWait` (`normalize_answer` refuses a quota-shaped model answer with `E_PROPOSAL`; an adapter reset is checked with `quota.within_bounds`, the same window `quota.read` uses, before any conversion or persistence, and one outside it is a retryable `E_EXECUTOR`). `QuotaWait` comes from three places: `daemon.tick` applies `quota.checked` to the JSON a configured resolution executor (`argv`) prints; `resolve` raises it when the Claude CLI reports a rate limit (`provider_wait`), and `CliModelExecutor.execute` turns it into `deferred`; a custom adapter's `deferred` envelope raises it after the `quota.within_bounds` check. Any other provider error reaches the editor as a retryable `E_EXECUTOR`. A structured answer may carry every schema field with the unused ones empty: `normalize_answer` ignores empty request fields and serves a request before anything proposed beside it, pages before reconciliation. The normalized answer replaces the lease only while that lease is held, before any publication. The rounds of one attempt (at most `MAX_ROUNDS`, five) form one model conversation: every `ModelJob('edit_pages')` carries `conversation` (`conversation.py`) with a key derived from the operation and the lease token, the turn number and, from turn 1, `message`, the payload keys that changed since the previous round (`changed`, `appended` for a list that only grew, `removed`). The payload itself stays complete. `CliModelExecutor`'s built-in Claude and Codex adapters ignore the field; `CommandExecutor` sends it beside the payload, and `kelmo executor` takes it out and hands it only to a custom provider, which may continue the earlier turns' conversation with `message` alone (`docs/EXECUTORS.md`).

Concurrency and crash window: an identical request while the lease is live gets `E_BUSY` and never calls the model or overwrites the winner. The attempt renews its lease by token before every executor call; the built-in CLI executor honors the 600 s deadline, inside the 900 s lease, and a lost lease stops the attempt with `E_BUSY` before another call. A custom `ModelExecutor` must honor its own deadline, also shorter than the lease; the lease token prevents duplicate publication, not extra model calls made by an unbounded plugin. Consultation refusals fixed by the request or the answer (`E_BUDGET`, `E_INPUT`, `E_CAPABILITY`, `E_UNRESOLVED`, invalid expansion, reconciliation or round exhaustion as `E_PROPOSAL`) settle the request refused under the attempt's token, so replay needs no model call and a corrected request can be requeued; executor/provider failures, interruption and quota release the lease so the same key retries. A process death after the model answered but before the answer was recorded leaves a lease that a retry takes over after it expires, and that retry calls the model again: the editor does not promise exactly-once external model execution. After the answer is recorded, retries and recovery never call the model. Budget failures retain their phase-specific behavior: consultation and an empty answer over partial context settle refused. A pre-preparation `engine.check_budget` failure keeps the request open with its saved answer, so repairing the configured budget permits retry without another model call. After preparation, a publication `E_BUDGET` still settles the intent refused; changing that recovery policy remains an open decision.

Under `.state/worker.lock` the editor refuses a dismissed source (`E_DISMISSED`) and a moved generation (`E_STALE`), and keeps the request open with `E_CONFLICT` while the working registry differs from the pinned one. It then normalizes the answer (facts, `fact_checks`, narratives, page title/summary/priority and new detail pages only; owners, evidence, protection, mandatory flags and actions are never proposed). Entries that restate stored content are dropped with their checks, so a restatement never rebinds an owner, predecessor or evidence; a current narrative restated with the same page, text and exact dependency revisions is dropped before the empty/partial-context gate. Fact, narrative, title and summary text is checked raw and through the file-contract Markdown parser: publisher labels (`[a:`, `[f:`, `[source:`, `[status:`, both unresolved-legacy labels, `Narrative: <id>.` and `State: current|stale.` anywhere, including link and image text) and action-panel declarations (`Subject: <kind>/<id>`, `Feature ID:`, `Work revision[ of <id>]:`, `Deployment artifact[ of <id>]:`, `Repository bindings:`; action projections are read for both topic and feature layouts), raw HTML, headings, publisher evidence/action tables, action projections and page navigation (wikilinks and scheme-less non-anchor links, which the contract counts as navigation) are `E_PROPOSAL`; ordinary Markdown, ordinary tables and external or anchor links pass. `semantic_projection` also runs the commit's managed-link audit on its projection and refuses new broken or ambiguous links with a typed `E_PROPOSAL` before preparation and again at publication, so an invalid proposal never becomes a prepared intent that blocks the shared recovery. Every new or changed fact needs a `fact_checks` receipt that `fact_checks.check` accepts, exactly as note promotion: `existing` with the current revision, or `not_found` with a search receipt bound to the same text, target and candidate snapshot (`E_FACT_CHECK` otherwise; no semantic fact is exempt). The verified receipts are stored in the intent and checked again against the registry immediately before publication. An empty delta settles `unchanged`/`archive-only` only on complete context; on partial context it is refused `E_BUDGET` naming the omitted pages. The editor then computes `engine.semantic_projection` (registry plus exact page bytes, unmanaged bytes kept); page baselines are the pinned generation bytes the model saw, and a working page that differs keeps the request open with `E_CONFLICT`, as does a render failure. Before preparation, `engine.require_clean_baseline` runs the commit's `git status` test over every file the real publication reads or writes (every registered and fact page, whose unmanaged bytes come from the working file, the registry and `generation.json`), and `engine.check_budget` applies the wiki budget to the next generation; both stay retryable (`E_CONFLICT`, `E_BUDGET`) with the request open. `_complete` reruns the clean check before publishing a prepared intent, after first recognizing an already committed result, so a later hand edit is a typed retryable refusal with the intent still prepared, never an untyped failure inside the commit. New page and narrative identities must stay outside the shared namespace of page, narrative and action IDs, checked in `normalize` and again in the authoritative transform (typed `E_PROPOSAL`). `fact_checks` entries need a string `fact_key`. A title change needs a publisher-generated H1 (`pages.owned_heading`), which is then rewritten with the title; a hand-written H1 is refused `E_OWNERSHIP` with the repair. The immutable intent's `KnowledgeProposal` carries the baselines and the source `EvidenceRef`. `engine.publish_semantic` re-reads that intent from the journal, recomputes the registry and bytes, refuses any difference, and commits through `_commit_registry`, which rechecks that a created page's file is still absent. Facts get the source as exact evidence and note; narratives record the source and the revisions of the facts/actions they depend on. A later fact or action change marks dependent narratives stale in the same publication; stale text is rendered quoted under a stale label. An archive-verified source with the same note hash and archive ID as an unresolved legacy note resolves that note and its facts to exact evidence without other changes; a different source restating a claim does not. A fact change in the same answer is checked against the revision the model read, and keeps that original revision as its single predecessor.

Feature navigation: `ownership_guard` refuses (`E_BINDING`) any write that changes which pages show a feature page, an accepted action subject or an enrolled feature, unless the new set equals the controller enrollment the editor was given through `contexts` (the same `ContextBindings.feature_pages` StateAPI uses, with this service's `OriginBindings`). Enrollment is never derived from model text; without `contexts` such navigation edits are refused. With `contexts`, every enrolled action subject (accepted or not yet materialized) is guarded too.

Outcomes per source: `applied`, `archive-only` (no change, or `dismiss`), or `unresolved` with the repair reason for budget, executor, quota, stale, malformed, fact-check, binding, unauthorized or ownership refusals; a prepared but uncommitted publication reads `unresolved` until it commits. The request state, its `editor_result` journal event and the source outcome commit in one journal transaction (`action_prepare`/`action_finish`/`action_refuse` with `outcome=` and `result=`, bounds validated before any row changes). The journal keeps the reference signatures `action_begin(..., outcome=)`, `action_finish(id, receipt, accepted, outcome)` and `action_refuse(id, code, message, outcome)`; an outcome is written only when that call settles the request. As in the reference journal, a StateAPI or Git request's outcome targets its own `operation_id` (for Git that is the intake) and is written as given; an editor request's outcome targets the archived source it cites (a different ID) and is monotonic: it never downgrades from `applied` and never changes after a dismissal. An editor request records `unresolved` ("editor request open") in the same transaction that begins it. A source still owned by the promotion/resolution lane (a resolution row, or a promote operation not yet applied) or an authoritative Git intake (a `git` request row, or a typed `git_event` packet) is refused `E_STATE` before any request, so the editor never races those outcome writes. A prepared, unpublished rule change rechecks at publication that its recorded origin is still the issued, requester-capable owner of the source; otherwise it is refused `E_ORIGIN`, while an already committed effect is still recognized. A refused request replays its refusal; requeue uses a new key. `rule_change=True` is a controller-only seam: it needs a requester-capable issued origin that also owns the archived source; serialized origins, payload text or proposal fields cannot set it.

`Service.knowledge_api.publish` publishes or replays only a proposal the editor prepared, matched exactly by `proposal_id`; any other proposal keeps the earlier refusal boundary (`E_STALE`, `E_OWNERSHIP` for managed regions, `E_CAPABILITY`). `executor.CliModelExecutor` adapts installed Claude/Codex CLIs or a custom command with explicit model and effort selection; the editor core never reads a provider transcript.

Page creation: a proposal page with `expected_revision: null` registers one topic or feature detail page (`page_id`, `layout`, `title`, `summary`, `parent`, optional `priority` and `links`). The target stays under `projects/<request project>/`, is neither registered nor redirected, and its file must be absent at preparation and again at publication (`E_OWNERSHIP`: an existing or newly appeared file, registered or not, is never claimed). The parent is a non-person page sent in full and gains the new page ID in its `links`; links name only pages sent in full; the page ID is new. Creation needs `contexts` (`E_BINDING` otherwise): a feature page takes exactly an enrolled feature identity at one of its enrolled pages, whose enrollment must also list the parent that now links to it; a topic page takes an identity that no enrolled subject uses; an enrolled topic, person or task subject never gets a page this way (publisher-assigned identities for those are an open decision). `engine.creation_problem` repeats the check at publication from the intent's `feature_enrollment` and `enrolled_subjects`. Kind, category and `feature_id` derive from the layout; repositories, aliases and tags stay empty. The proposal baseline of a created page is the SHA-256 of empty bytes. Two editors creating one target: the later one is `E_STALE`, and a requeue is refused because the target is registered.

Rule changes: under `rule_change=True` an existing protected rule can be edited and a new person-page fact becomes a protected rule (`owner: rule-policy`, `protected`, `mandatory`); outside it, no answer can set or clear those fields. Every person-page fact is `mandatory` either way.

Recovery: `publication.recover_publications` is the one recovery that StateAPI, Git ingress and the editor run under the worker lock their caller holds. It finishes the wiki transaction, then every prepared StateAPI and editor intent from the journal in preparation order, without a model call. A typed refusal settles only its own request; an intent still prepared after a failure stops the caller. The editor also runs it before reading a generation for a new request, so a recovered action is visible to the model instead of making the answer stale.

Requeue, dismiss and deferral: `Service.editor.status(source)` reports the outcome, the recorded quota reset, whether it was dismissed and every editor request. `requeue` runs a new request only for an `unresolved`, undismissed source without an unfinished request. `dismiss` applies only to a never-applied, undismissed source with editor work that is open or ended unresolved (`E_STATE` otherwise, including sources with no editor request); under the worker lock it refuses every open request, consulting ones included, with `E_DISMISSED`, records an `editor_dismissed` event and `archive-only` in one transaction (a reason over the outcome bound is `E_OUTCOME` before anything changes), so a model answer that returns later is refused. A `deferred` outcome records an `editor_deferred` journal event; until its reset time a request for that source raises `QuotaWait` without invoking the model. A prepared intent whose publication fails (local changes found by the recheck, or a non-typed Git failure) stays prepared and blocks later publications until the working tree or repository is repaired. Open decisions: who may dismiss (any issued origin today); whether an editor may admit a forgotten or superseded archived source (the adoption contract excludes hidden evidence from public reads and keeps exact-citation verification, but sets no rule for admitting new editor claims from it); whether dependencies stay editable. The create CLI/MCP path queues editor work for the daemon. Shared creation, promotion and resolution carry the server profile's trusted ContextBindings, so enrolled page creation and feature navigation can run. Local library integrations must supply their own trusted enrollment. Dedicated editor requeue/dismiss controls remain library methods; the request fingerprint does not include contexts.

### Dreaming

`Service.dreaming` (`Dreaming(service)`) runs bounded passes over new evidence archived after a durable cursor (`dream_state.cursor`). Durable tables `dream_state`, `dream_findings` and `dream_runs` are initialized on first use in the journal. `Dreaming.pause()` and `Dreaming.resume()` update the paused state; when paused, `Dreaming.run` returns immediately. `Dreaming.run` reads the pinned committed generation (`E_GENERATION` without one). `Dreaming._changed_evidence` selects up to `max_sources` archived operations strictly after the cursor, ordered by `created_at` and `id`. Dreaming's own notes (prefixed with `dreaming-` or recorded in `dream_findings`) are skipped. An in-flight operation that is neither archived nor applied stops the cursor scan.

`Dreaming._packet` gathers evidence text via `Service.show` and finds related non-person wiki pages via `Dreaming._related`. It queries pages whose facts cite the archive IDs, followed by their graph neighbours, excluding person pages. If an evidence item exceeds `budget_tokens`, it is recorded in `skipped` so the cursor is not held. Related pages that exceed the budget are named in `omitted`. `ContextBundle` records completeness.

`Dreaming.run` invokes `ModelExecutor.execute` with `ModelJob('dream', bundle, packet)`. In `executor.py`, task `'dream'` selects the `DREAMING` prompt and `DREAMING_SCHEMA`. Quota deferral records `deferred` with `reset_at`. Validated findings in `Dreaming._validate` must cite shown sources exactly: facts at exact revisions or evidence at exact versions. Similarity alone is rejected. Findings are restricted to `link`, `contradiction`, `merge` and `split`. Page targets must exist in shown pages. A link finding must start on a project page, contain two targets, and link to a page not already linked.

Accepted findings are recorded by fingerprint in `dream_findings` via `Dreaming._record`. Re-observed findings increment `seen` and update `last_seen`. For open link findings, `Dreaming._publish` checks staleness via `Dreaming._stale`: if any cited page revision, fact revision or evidence version changed, the finding transitions to `stale`. Otherwise, it captures a Markdown note titled `# Dreaming link finding <fingerprint>` (`NOTE_PREFIX + fingerprint[:16] + '.md'`) with `Service.capture_source`, archives it via `Service.run`, and calls `Service.editor.edit(..., link_pages=True)`. In `editor.py` and `wiki/engine.py`, `link_pages=True` accepts `add_links` on sent pages, appending page IDs without rewriting facts or other links. Environment errors leave findings `open` for future retry via `Dreaming.publish`.

Dreaming never mutates action state. It cannot complete, retire or reopen work by age or lack of activity. It never proposes status, action, ownership or protection changes, and never rewrites facts. It holds the worker lock only during editor publication. Contradiction, merge and split findings are recorded for review and never published automatically.

### Automatic sessions

Fresh mode is off. `auto` and `archive-only` are explicit; reinstall without an option preserves settings. Selected provider roots enroll allowable transcript paths. Complete malformed JSONL records fail; partial final bytes are preserved and do not count as processed. Truncation/replacement starts a new generation. Duplicate events reuse identity `(provider,node,session,generation,range,task)`.

Stop captures and schedules after configured new user turns (default 30); PreCompact forces checkpoint scheduling; SessionEnd schedules finalization. Finalization uses the complete captured generation; checkpoints use uncovered ranges. `extraction = "tail"` (default) sends one chunk of the newest evidence per job and reports `omitted_pieces`; `extraction = "complete"` chunks every selected message within ceilings. Hooks capture/schedule only, model calls run in the existing worker. Native event delivery is still a host acceptance gate.

`session_worker.tick` -> `_run` -> chunk extraction -> validated note -> saved output -> archive via Service -> saved receipt -> optional candidate reconciliation -> `Service.propose_archived_note`. That last method checks source/archive equality, then hands the saved proposal to `Editor.edit` as `DeclaredChanges` (key = the session application identity, fingerprint bound to the proposal digest, `rule_change=False`), outside the worker lock the editor takes itself. Extraction receives the registered page targets as `pages` and names candidate targets from them.

Invalid/uncertain candidate facts do not discard a valid archived note. Outcomes include `wiki_applied`, `wiki_unchanged`, `skipped`, `needs_review`, `wiki_needs_review`. Attempts and accepted intermediate output survive crashes. Off/paused stops future work/capture, not an already running executor.

Manual `sessions run --executor-config` wins over saved configuration. Without it, saved session extractor wins, then the default resolution executor. Background ticks retain the configured extractor preference. This priority has three regression cases.

### Stopped-copy snapshot and cutover

`snapshot.take_snapshot(sources, destination)` captures named `sqlite`, `git` and `tree` sources into an empty directory while writers are stopped. It establishes a double-read barrier: every source is fingerprinted before any copy begins, and re-fingerprinted after all copies complete. If any source changed during the copy, the destination is removed and `take_snapshot` raises `E_SNAPSHOT`. SQLite databases are copied via `sqlite3.backup` using read-only connections and checked with `PRAGMA integrity_check`. `snapshot.archive_census` records all current and historical record versions and content hashes. `snapshot.journal_census` records operations and action requests. Git repositories require a clean status (`git status --porcelain`) and record HEAD, refs, and file mode hashes. Plain directories are recorded as `{relative: 'sha256:mode'}` by `snapshot.tree_files`. A symlink is never followed: a Git source records it as `link:<sha256 of its target text>` and the copy recreates the link; a plain `tree` source raises `E_SNAPSHOT` on one. The snapshot writes `manifest.json` with schema 1 and a content digest.

`snapshot.verify_snapshot(snapshot)` verifies `manifest.json` against its hash and re-checks every copied database and file map against disk. `snapshot.inventory(snapshot, queues=())` assigns exactly one disposition to every operation, request and record. Journal operations with archived evidence become `import`; terminal operations become `carry-unresolved`; in-flight operations become `resume-after-cutover`. Action requests in `open` or `prepared` state become `settle-before-cutover` (blocking cutover). Queued jobs in tree sources become `drain-before-cutover` (blocking cutover). Duplicate item identities raise `E_SNAPSHOT`.

`snapshot.import_snapshot` unpacks a verified snapshot into a schema-2 vault with independent roots (`state_root`, `archive_root`, `knowledge_git_root`). Progress is tracked in `.import/state.json`. The process is resumable step by step:
1. `vault`: copies Git history to `knowledge_git_root` using temporary staging, proving file maps match.
2. `archive`: places `archive.db` into `archive_root`, proving file SHA-256.
3. `journal`: places `journal.sqlite3` into `state_root` or initializes a fresh journal.
4. `sources`: optionally places captured source bytes into `state_root/sources`.
5. `config`: writes schema-2 `kelmo.toml` with `[storage]` roots and verified carried settings from `snapshot.carried_settings`. Reserved settings (`schema_version`, `writer`, `vault_id`, `node_label`, `wiki_root`, `storage`) are excluded.
6. `wiki`: claims the placed wiki for the importing authority (`engine.activate_wiki` writes `kelmo-owner.json` inside the wiki's Git metadata), so publications after the import do not refuse with `E_WIKI_OWNER`; a copy another vault already owns refuses here.
7. `open`: instantiates `Service(control)` to perform in-place schema upgrades and authority registration.
8. `verify`: proves that archive record versions, Git HEAD, Git refs, journal censuses and source files match the snapshot manifest exactly.

`snapshot.mark_cutover(control)` requires verified import completion and writes `.import/cutover.json` as the baseline. `snapshot.tail(control)` computes writes accepted after cutover: new archive record versions, Git commits between baseline HEAD and current HEAD, and new or changed journal operations and action requests. `snapshot.rollback_check(control)` raises `KelmoError('E_TAIL', ...)` if any tail writes exist, refusing rollback to the pre-cutover snapshot. `snapshot.forward_recover(control, snapshot, destination, roots=...)` handles post-cutover disaster recovery: it refuses while an unfinished wiki transaction exists, captures a fresh snapshot of the current vault including its tail, imports it into a fresh destination, verifies no accepted tail writes were lost, and marks a new cutover baseline.

## Read flows and failure behavior

HOT: `Config + hot.render(cwd)` reads ordered global pages then deepest matching project/worktree roots; deduplicates pages. No recursive imports, symlinks or partial page delivery. One invalid/oversize page fails the entire context; hook returns a diagnostic. Missing config gives empty HOT. Globals selected when no cwd; supplied cwd absolute. `max_bytes` is full UTF-8 block size, not tokens. Every call rereads; active conversations need another invocation to refresh. Without a committed registry, multiple page reads are not a transactional snapshot.

HOT with a committed registry: when HOT is configured and the bound registry is committed, `hot.render` reads every page from the one generation `KnowledgeReader.generation()` returns for the committed HEAD. It never reads working-tree pages, so an unpublished edit, a prepared action intent or an interrupted publication is not delivered as current. A configured page missing from that generation fails with `E_HOT`. A missing or corrupt manifest fails with `E_GENERATION`. Whether a registry is committed is read at HEAD; unpublished removal, downgrade or damage cannot switch delivery to working files. Mandatory content is whole pages from `pages.mandatory_paths`: `person.md`, every registered page with category `you` or layout `person`, and every page holding a mandatory or protected record. These pages come first, and no person fact needs a flag. Then come the configured global and project pages from the same generation. Root selection is unchanged: only `kelmo.toml` roots select a project, and payload `cwd` cannot enroll one. The context opens with one line naming the publication ID, manifest prefix, freshness, completeness and mandatory pages. `max_bytes` still counts the whole UTF-8 context, including that line. If the line plus the mandatory pages exceed it, the result is `E_BUDGET`, and the hook reports `Kelmo HOT incomplete (E_BUDGET)` with no pages. If the selected maps exceed it, the result is the existing `E_HOT` refusal. Nothing is truncated. `render` also returns `generation`, `freshness`, `complete` and `mandatory`. The hook passes a full service's trusted `service.knowledge` reader, which is bound to the same repository or refused with `E_BINDING`. The native `hook start` command has no service and builds a reader from the same configuration. An unconfigured HOT stays empty.

COLD: `Service.search` delegates to the archive adapter. Only embedding failure triggers lexical FTS5/BM25; DB failures propagate. Public CLI/MCP returns `{items, search:{mode,degraded,reason}}` even for empty fallback results. Internal Python keeps list compatibility unless `with_metadata=True`. The existing filter surface is preserved. Ordinary intake uses `durable-text/1` with pending vectors during model outage. Archive search is not authoritative current wiki state.

Configured chunk index (`[embedding]` present). `Service` builds the configured provider once (`embeddings.provider_from_settings`, no inference) and hands it, the settings and the chunk sizes to `LocalArchiveAdapter` as one `ChunkIndex`; capture, update, search, expand, backfill and rebuild all use it, and no other model or channel stands in when it is down. The chunk window comes from the declared settings: a local provider's own tokenizer, or for a broker the local `tokenizer` file plus the declared `[embedding.input]` table (`max_tokens`, `query_prefix`, `document_prefix`, `special_tokens`), which must name the same input path as the declared space's transforms. So a cold or absent broker still cuts and stores chunks; it never supplies a verified space identity, and vectors stay pending until it answers.

- Capture/update: cutting and inference run before the write transaction; under `BEGIN IMMEDIATE` the adapter rechecks the head version, content hash and profile, then writes chunks, chunk FTS and verified vectors with the record and its receipt. An outage keeps text, metadata, chunks and FTS and reports `vectors_pending=true`; `require_vectors` refuses and writes nothing. A text update replaces the chunk generation (old vector bytes without a recorded space are copied to `unverified_vectors` first); a metadata-only update keeps chunks and vectors; a no-op or replay writes nothing.
- Search: `search_records` (behind `Service.search`) keeps the record shape, one item per record holding the present version's row, ranked by `search.search_chunks` over every query variant with filters, precise `COALESCE(valid_from, created_at)` date bounds and visibility applied before ranking. Hybrid degrades to BM25 with the provider's reason; semantic raises `E_EMBEDDING`; partial coverage is `partial_vector_coverage`; records without current chunks are added through the record index and labelled `unindexed_records`. The limit counts records: `search_chunks(record_limit=…)` stops fusion at a bounded record pool (limit plus a few, at most `MAX_RECORD_POOL`, two chunks per record at most), while its `limit` stays a chunk-row count; each ranked record is re-read and kept only if still visible at the same version and hash, so a record hidden or changed after the ranking snapshot is dropped, never returned. `ArchiveAPI.search(variants, …)` returns `EvidenceRef`, `ChunkLocator` and the index identity; `expand` refuses a locator of another generation (`E_CAPABILITY`), a changed record (`E_CONFLICT`) or a hidden one (`E_FORGOTTEN`).
- Maintenance: `LocalArchiveAdapter.backfill_vectors`, `rebuild_chunks` (explicit reembed, which first sweeps every space-less vector into `unverified_vectors`), reached through `kelmo admin backfill` and `reembed` ([CLI.md](CLI.md)). Low-level `memory_delete` copies space-less vectors before deleting, refuses a caller transaction and refuses an archive Kelmo owns (`kelmo.store.db.managed_archive`); the `kelmo admin` verbs refuse it the same way.

Administration: `archive_admin.ArchiveAdmin` holds every operator verb (count, stats, doctor, backup, dump, graph, entity-index, reembed, backfill, search-log, purge-plan, purge-authorize, purge) behind an `AdminGrant` that `operator_grant` issues per vault and per verb; `kelmo admin` issues one for the invoked verb (`purge-authorize` is issued the `purge` capability), MCP never does. The grant is a capability check for cooperating code, not a security boundary. `READ_VERBS` (count, stats, doctor, backup, dump, search-log) take the vault's `Config` and read-only connections: no adapter, schema step, writer row or repair, so they work when `Service` cannot open; the others need the `Service`. They do not change what they read, except that `search-log` with an explicitly configured `[telemetry]` table first applies its retention in a separate write transaction. Stats and doctor read `kelmo.store.memory.stats` and `kelmo.store.doctor` (`archive_checks`, `dependency_checks`, `overall`: healthy/degraded/failed) and the read-only graph state of `kelmo.doctor`; `service.chunk_index_for(Config)` gives them the index identity without inference. Backup and dump write the integrity-checked sqlite backup snapshot to a temporary file and publish it by hard link, never replacing a path and never inside `.state/`, `archive/` (backups excepted), `.cache/` or `.git/`; rotation touches only backups listed in the directory's `.kelmo-backups.json`.

Search telemetry (`kelmo.store.memory.search_log`) is off unless `[telemetry]` selects `redacted` or `full`. `Service.search` hands one row, with the retrieval identity (contract, index/generation, model, space, profile), to `search_log.record`, which opens its own connection and `BEGIN IMMEDIATE`, replaces ids of records purged meanwhile, prunes by age and row count and swallows any failure. `ArchiveAdmin.search_log` applies a configured retention (`enforce_retention`) before reading and is the only reader; with no `[telemetry]` table nothing is pruned, and a mode change rewrites no row. Behind a transport archive (a server's confined child, the only writer of `archive.db`) the parent process logs the same rows to `<state root>/telemetry.sqlite3` (`kelmo.telemetry`, created owner-only), with the enrolled client the search came from as `client`; `ArchiveAdmin.search_log` reads both logs, a purge rewrites the purged id in both, and `admin stats` adds `server_searches_logged`.

Physical purge (`ArchiveAdmin.purge`, `ArchiveAdminAPI`) is two operator steps under the purge capability. `plan_sha256` is the operator's review identity (archive-side dependents plus every required action and refused key); `archive_sha256` is the separate archive compare-and-swap that `apply_purge` rechecks (stored as `archive_purges.plan_sha256`). Knowledge dependents come from the committed registry (`engine.git_blob(HEAD:knowledge/provenance/registry.json)`); an unfinished wiki transaction, a working registry that differs or has no committed generation, or an invalid committed one refuses planning with `E_CONFLICT`. Rows of the composed state/editor journal tables `action_requests`, `action_intents` or `editor_intents`, when they exist, that mention the record or its bytes are refused `intent:` dependents. `ArchiveAdmin.authorize_purge(archive_id, disposition_id, plan_sha256)` (`kelmo admin purge-authorize`) takes the capture lock, computes the full plan again, refuses any refused dependent or a hash that is no longer current, and stores the disposition in the journal's `purge_dispositions` table (vault id, operator principal, record, plan hash, one action per required dependent, state `authorized`) through `Journal.authorize_purge`: same id and payload replays, a reused id with other content is `E_IDEMPOTENCY`. `purge` reads it back through `ArchiveAdmin.stored_disposition`, the default disposition source of a Service-backed `ArchiveAdmin` (an injected source is still accepted); nothing authorizes on the way. Archive and journal connections must be idle before anything changes. Accepted facts, notes, session application receipts, unsettled resolution jobs and any external claim row on a dependent operation are refused dependents. Under the worker and capture locks the plan and disposition are checked again (a disposition already settled while the archive holds the record again, as after a restore, refuses with `E_STATE`); `Journal.begin_purge` then rechecks external claims and records a `purge_intents` row in one transaction, `Journal.claim` refuses its operations while it executes, `abandon_purge` withdraws it when the archive half did not commit, and a replay rechecks `external_claims` and reports a leftover row as a refused `lease:` dependent without clearing it; `LocalArchiveAdapter.purge_dependents` and `apply_purge` turn `secure_delete` on before the first delete (restoring the caller's setting), recheck writer and plan hash under `BEGIN IMMEDIATE`, remove the coordinator rows and call `delete.purge_rows`, and write `archive_purges` plus tombstone keys (operation, content, source) that `capture`, `update` and `_row` consult (`E_PURGED`, checked before work and inside the insert transaction). The journal then hands over dead local claims, stages dependent operations `purged`, which `Journal.get` reports as the terminal `durable_stage`, and `Journal.settle_purge` finishes the intent and marks the disposition `settled` with its receipt in one transaction; a queue retry of a purged operation is the ordinary terminal `E_STATE`, while archive capture/update of tombstoned keys is `E_PURGED`; a repeat after a crash between the stores completes the journal half from the stored archive receipt. Spool bytes, journal and Git history, older WAL frames and pages freed earlier without `secure_delete` are retained and declared.

Hiding: `Service.forget` delegates the visibility marker to the archive adapter and records the owning operation's forgotten stage; a repeat preserves the first timestamp. Search/list exclude hidden rows before the limit and public show refuses them. `Service.archive_record` requires a matching journal owner for internal hidden-record access and verifies the exact owning receipt; the caller's serialized origin is insufficient. Status retains stored-record and forgotten-record counts. `forget` remains CLI-only and does not physically remove evidence; physical removal is the separate administrator purge above.

Pre-clear review: readonly snapshot hash/current-file comparison, generations, pending/failed jobs, below-threshold records and incomplete tail. With no session identity it is only global queue state. `semantic_completeness_guaranteed=false` always. Review neither captures missing bytes nor blocks native clear.

Graph: `Graph(Service)` binds to `Config.wiki` and the selected archive. IDs are NFC-normalized relative paths without `.md`, preserving case, punctuation and Unicode. Exact paths take precedence; convenience names/aliases require a unique match. Explicit relative wikilinks can traverse within the selected root. `markdown-it-py` excludes code examples and embeds; YAML metadata supplies title, aliases, status, parent and tags. Edges retain file/line evidence for `links_to`, `child_of` and `tagged_with`.

Publication also computes derived topology (`kelmo/store/graph/analysis.py`: Louvain seed 0, hub threshold, cross-community surprises) and rebuilds `entities_fts` (`graph/index.py`) in the same savepoint. Analytics answers carry `analysis` (`verified: false`, snapshot digest, `implementation`, `assignment_sha256`); a named `snapshot` or `assignment` that is no longer current refuses with `E_GRAPH_STALE`; the binding's `analysis_version` and `analysis_implementation` (networkx release) make pre-analytics or other-implementation snapshots stale. Nodes keep `community_id`, `surprise_score` and `is_god_node`, and every query answer, navigation included, carries the `analysis` label for them. A plain link resolves exact ID, then the linking page's own folder, then a unique short name (the publisher's order). Shorthand and alias lookup match pages only; `tag:`/`unresolved:` nodes are reached by exact ID. Template-named documents keep their canonical identities and links. A database error in the read phase is returned without recording a failed publication. See [GRAPH.md](GRAPH.md).

The scanner reads through directory descriptors without following descendant symlinks, then rereads file bytes and directory/file identities to reject an inconsistent scan. Each query/read compares its content digest and vault/wiki/version binding with `archive_meta` graph metadata. Missing or stale caches rebuild synchronously under the graph lock. Graph rows, FTS effects and snapshot metadata publish in one savepoint; caller transactions are retained. Failure keeps prior rows and returns an error. A valid empty wiki publishes an empty index. This covers changes from wiki publication, manual edits, rename/delete and relocation on the next access, without another worker.

`graph stats` and doctor inspect absent/current/stale/failed state without creating cache state. `graph read` returns content from the same scanned snapshot; it never opens a path supplied by graph rows. Radius is at most two, results at most 200, and a shortest path exceeding the ceiling returns an explicit limit result. Database errors propagate rather than becoming empty search results. The public CLI and MCP use this Service path.

MCP startup checks the selected provider's health and input identity when
`[embedding]` is configured. It does not load the unrelated record model or
report its missing cache as the configured provider's failure. The startup line
names the local or broker provider. Configured providers belong to each worker's
Service and load separately; only the legacy record model has a process-wide
cache. Startup verification does not guarantee that a later broker request succeeds.
An archive adapter that owns its provider without exposing local warm-up is
reported as unsupported for warm-up, without claiming an embedding outage.

## Project hub lifecycle and delivery

`projects.py` owns project add/link/unlink/rename and the shared resolver used by CLI
preview and hooks. Add and rename persist a recoverable intent before changing the
HOT configuration; the publisher commits the registry, wiki, generated views and
generation together. Existing selections without a project map remain deliverable.
Old-format generations keep the legacy reader until their next publication.

`hub_delivery.py` validates complete generation sets and publishes a cache pointer.
Each shared binding retains its immutable set name. Offline replay checks the latest
known enrollment revision before reading that set. Cache metadata is bound to its
directory name by hash; verified server responses may repair content damage without
lowering the generation or enrollment floor. Metadata damage remains a refusal.

`hub_embed.py` updates only opted-in instruction blocks. Those blocks contain the
published combined view; work-page additions and pending notes stay in hook output.
The server filters pending notices through the same enrolled project boundary as hubs.
Hook delivery acknowledges only after stdout flush succeeds. Pending read failures keep
published HOT available with a warning and no acknowledgement. Local view pointers use
the existing immutable set cache; omitted work/pending and legacy context use private
content-addressed JSON references under `hub-context`. Those files retain the complete
source for the emitted pointer, including during offline delivery.

## Verification and context pitfalls

Source invocation must select `src`; a developer venv can carry a stale wheel. Installed tests require `KELMO_TEST_PREFIX` pointing at the fresh candidate. Default source acceptance excludes experimental `test_runtime.py`, `test_runtime_macos.py`, `test_linux_runtime.py`, and separately executed `test_installed_cli.py`. CI configures source and installed checks on macOS/Linux with Python 3.12/3.13, sharing one wheel. Distribution checks compare Python/schema and shared-entrypoint bytes across source, wheel and selected runtime. Native platform/client and remote-run evidence remain separate gates.

Run audits against an explicit sandbox path and synthetic inputs, never a real HOME. Only read logs that belong to that fixture. No test requires private wiki content or a live archive.

When implementation changes, update this document's affected flow or invariant and the matching product feature status.
